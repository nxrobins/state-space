# 3D milestone 3: a finite chunked world

M3 adds a 64³ world SDK and seeded first-person cavern, retaining the exact
`ca-3d-m1` law and the existing 32³ runtime. The shipped 2D bundle remains
SHA-256 `0862c671ccb7d051697b47bd62760e36e04402b232035006f8935744d790a4eb`.

## Runtime and limitations

The [Cavern README](../../examples/cavern/README.md) specifies the SDK, generator,
tools, scheduling, snapshots and controls. The new CPU/GPU entries are
`state-space-engine/experimental/3d/world` and `/world/gpu`. Default geometry is
eight complete 32³ chunks in a closed 64³ world; other complete partitions up to
64 chunks are accepted for verification. This milestone has no streaming or
sleeping simulation regions.

The CPU reference uses global linear arrays. GPU arrays use chunk-major storage,
with local X/Y/Z order. Pair parity, neighbor selection and gas tie-breaking use
global coordinates and the global linear index, never storage addresses.
All chunks share one completed tick. Each immutable-input pass gathers across
seams directly from resident storage and writes its own output cell; GPU dispatch
boundaries order the full world between passes. No halo is independently advanced.

All nine M1 materials and the existing integer thermal/phase rules are unchanged.
World snapshots have a separate versioned envelope and validated canonical chunks.
Restore may repartition storage but cannot change world geometry, physics identity,
catalog or state. Placement and external-energy edits retain exact accounting.
M1/M2 snapshots and their 32,768-cell cap remain intact.

Persistent GPU face lists rebuild after material changes; seam edits invalidate
face neighbors. Temperature-only changes use current resident state for shading.
All dirty chunks are updated regardless of visibility; conservative chunk-sphere
frustum tests only omit draws. The explicit mesh inspection hook is diagnostic.

The `cavern-seed-1` generator uses integer hashes, ellipsoid tests and fixed rules
for seed-dependent chambers, strata and finite water pockets. An authored central
challenge guarantees an accessible route through a dam, flowing water, freezing
and an ice crossing. Its water and thermal interactions span XYZ chunk boundaries.
The game version is `volume-cavern-1`; integer input tapes bind the complete world,
seed, actor and events. Camera trigonometry is quantized before recording input.

Stone/ice/glass remain fixed. Pressure, stored material velocity, combustion,
structural support/collapse, character forces, custom 3D registries and infinite
world streaming remain outside this milestone. Water is opaque. Larger worlds
and other hardware require separate measurements.

## Verification safety

The original test configuration allowed independent native conformance, structure
and SDK GPU fixtures to run concurrently. A separate CPU replay was also running.
Some demo tests submitted 132 synchronous ticks without progress or a yield.
These were concrete workload-control defects. A wider 24-hour log review confirms
unexpected reboots at 00:24,01:23,02:19 PDT on October 14. Their Kernel-Power 41
records contain bugcheck code zero. No matching display-driver, WHEA or memory
exhaustion event or recent crash dump was found. The precise hardware/driver cause
of the reported whole-computer freeze remains unconfirmed; a dirty-reboot record
alone does not identify it ([Microsoft's Event 41 guidance](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/event-id-41-restart)).
See the retained [event review](volume-m3/safety/event-log-review.json).

Verification now shares one OS-backed lease. Vitest files and Node test files
run sequentially. On Windows, the supervisor starts a suspended child, assigns
its entire descendant tree to a [Job Object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
then resumes it. The job limits committed memory to 8 GiB and processes to 64;
correctness runs use below-normal priority and a 25% aggregate CPU cap. Frame
measurement retains normal priority without a CPU cap and runs separately.

The supervisor records progress and stdout/stderr, checks every 200 ms, and
terminates only its own process tree on cancellation, a two-second monitor stall,
40 seconds without output, the bounded job deadline, or supervisor exit. Create
`dist/verification/<run-id>/cancel` to stop a job. OS locking prevents stale leases
after crashes. Regression tests verify exclusion and descendant cleanup using
CPU-only dummy jobs, including a deliberately timed-out child tree.

CPU trajectories yield between exact ticks and report intermediate progress.
Browser conformance submits one tick at a time with a five-millisecond pause;
it never submits a long 64³ batch. Benchmarks still perform one complete gameplay
tick per display callback, with one frame in flight. A frame exceeding 100 ms of
work or 250 ms from callback timestamp aborts measurement. Paused viewers stop
redrawing an unchanged view. These controls bound submitted work and cleanup;
they cannot guarantee recovery from a fault inside a display driver.

## Verification status

**Correctness, exact replay and both 60 Hz frame gates pass.** The serialized
72 engine tests and 21 rendering/controller tests pass, including 4,416 existing
native GPU/CPU pass comparisons. SDK builds, engine/Cavern structural lint,
type checking and three CPU-only supervisor regression tests pass. Real installed
Python/Node SDK clients match all 69 pass deltas; the installed world entry resumes
exactly, rejects unavailable Node WebGPU, and compiles with both TypeScript versions
without native WebGPU global declarations.

The M3 CPU reference completes 1,024 ticks, repeats under a 16³ partition and
resumes from tick 509 with both coordinates identical and zero drift. Hardware
WebGPU matches 270 isolated pass comparisons under 2³/4³ partitions at ticks
0,1,3,2³²+1 and near the safe-integer limit, plus composed schedules. The complete
64³ cavern matches at ticks 3,31,32,509,1024; restarts at 3,31,32,509 reach the same
complete final state. Cached face lists match an independent exposed-face oracle,
including interior/corner edits, seam neighbors, thermal-only geometry reuse,
dynamic movement and camera isolation.

The complete 600-command Cavern game matches Node in terrain, energy, player,
seed, look and events. CPU restarts at 31,157,509 and GPU restarts at
3,31,32,157,509 are exact. The route wins on tick 215 and walks on actual frozen
water. Initial energy is 1,344,408,320 Q; edits remove 232,797 Q; final energy is
1,344,175,523 Q with zero drift. Final game SHA-256 is
`ae097c577df49a0b8142d11bce9b0de23cffa500672feb594de30e49cc4ce2ea`.

UI controls, file import, invalid-file rollback, same-tick restore redraws, idle
paused rendering, the actual Watch the route button, partial benchmark cancellation
and Reset after an injected software error pass. The recovery test does not crash
the hardware driver. The existing M2 browser suite also passes all 675 isolated
passes, three 1,024-tick scenes, gameplay restarts and recovery checks.

CPU reference receipts bind their exact simulation inputs and retain the complete
source manifest from that run. Browser receipts independently bind the current
GPU/UI source before and after execution and the immutable Node receipt hash.
They reject changed CPU inputs. This permits presentation or GPU work to reuse an
unchanged independent CPU oracle without repeating thousands of CPU ticks.

Publication normalizes doubled CR line endings in the Cavern HTML. The original
page and a token-equivalence check are retained in
[publication evidence](volume-m3/publication/normalization.json); tags, attributes,
and all non-whitespace text are identical. Simulation and rendering code are
unchanged. Raw verification output remains byte-for-byte intact.

### PR 19 input-validation follow-up

CPU worlds now reject an explicit `edits: null` before advancing or changing
accounting, matching the GPU backend. Only an omitted or undefined edit batch
defaults to an empty array. The CPU regression failed before the fix and passes
afterward for both zero- and one-tick requests.

A standalone hardware test runs in an isolated 8³ world with no game loop or
renderer. Both backends reject null, false, zero, an empty string, an object and
a sparse batch at zero and one tick: 24 rejections preserve the complete state,
completed tick and nonzero external-energy ledger. Omitted, undefined and empty
batches then advance identically. This test also runs in full Cavern verification.

Fresh bounded checks pass: 74 engine tests, 21 rendering/controller tests, SDK
build, lint, type checking, three supervisor tests, and installed Python/Node SDK
clients with both TypeScript compilers. The installed world entry explicitly
checks null-batch rejection and exact state/accounting preservation.

The original frame/replay receipts and their bindings above remain immutable.
The rebuilt 2D, M1/M2 and world GPU bundles are byte-identical to the reviewed
head `3e73032731fb6f4b3c629907d8bb3aab024d3daf`. The CPU world bundle differs only
in its edit-default expression; all valid-input physics paths are unchanged.
Frame benchmarks were therefore retained rather than rerun. Current source
hashes, the exact change proof and fresh receipts are bound in
[the review-fix manifest](volume-m3/review-fix/bindings.json).

## Full-frame measurements

Separate fresh hardware browser sessions measured each scene sequentially, with
60 warmup frames, a reset, and 600 measured display-paced frames. Both the canvas
and browser viewport were 1920×1080 at device scale 1. Recorded hardware is an
i9-11900K / RTX 4090, driver 595.79, hardware-accelerated Headless Chrome 155.
Before measurement, the inventory recorded 2% CPU and 2% GPU utilization. No
background applications were terminated.

Each measured frame includes input, sparse edits, every physics pass over the
complete world, bounded collision readback, actor update, HUD, terrain mesh work,
uploads, draw, validation and GPU completion. Setup, warmup/reset, snapshots,
hashing, reference replay and OS scanout are excluded. There is no simulation
sleeping, visibility-based stepping or reduced rendering after winning.

| Measured frames | 600 | 600 |
| Median / p95 completion | 5.0 / 6.2 ms | 5.5 / 8.1 ms |
| Worst completion | 11.8 ms | 9.6 ms |
| p95 physics + query + controller | 1.4 ms | 4.5 ms |
| p95 terrain rendering + HUD | 4.8 ms | 4.8 ms |
| Actual physics cadence | 59.92 Hz | 59.94 Hz |
| Display callback cadence | 59.95 Hz | 59.95 Hz |

| Active route p95 / worst completion | 6.3 / 7.1 ms | 8.1 / 9.6 ms |

The 64³ CPU reference's 600 ticks after 60 warmup ticks measured median 59.1 ms,
p95 65.7 ms and worst 81.1 ms per public physics tick. These are diagnostic CPU
timings under the bounded correctness profile; the five-millisecond cooperative
pause is outside each tick sample. There is no CPU 60 Hz claim.

The guarded test suite recorded a 19 ms maximum supervisor delay; the long CPU
reference recorded 35 ms; the M3 hardware browser and frame runs recorded 19 ms;
the M2 regression browser recorded 50 ms. None crossed the two-second stop threshold.
These results cover the recorded
finite levels and hardware, with opaque diagnostic water and the current 3D
directional/thermal shading. They do not establish larger-world, other-device,
infinite-streaming or the separate 2D effects-stack performance.
