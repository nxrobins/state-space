# Two-choice crossing preview

One dedicated Worker owns a committed world snapshot and computes two possible four-tick forecasts by alternating short intervals of work between them while the presentation plays. The client supplies two distinct ordered edit sequences. In the benchmark they are left and right lateral impulses for the engineer. An accepted `set-choices` message replaces the menu, invalidates outstanding selections and returns a new generation without advancing the world. The worker receives the current state and the requested edits. The hosted reference packet and future selections stay with the client.

An `init` or restore returns a new generation, including when the restored snapshot has the same tick. A preview carries that generation, the base tick, a strictly increasing request ID and all four ordered edit batches. A newer selection supersedes the earlier one. Commit and cancel require the matching generation, tick and request ID. Commit publishes the selected branch once. Speculation uses the ordinary CPU world with the same work accounting and rejection behavior. Background and foreground work yield between bounded advances so cancellation and restore can interrupt a running branch.

Hosted CPU compares the changed-command trajectory with the digest recorded by the independent pre-PR worker. It also replays the original frozen crossing. The changed workload adds a lateral impulse on every request. At tick 104 the engineer also brakes, making the complete edit sequence a fresh request. The hosted prepared run waits for both choices before submitting and records that wait separately. Its timing ends at the worker reply.

On the cleared Mac the fixed stages `battlefield-prepared-visible` and `battlefield-fresh-visible` consume the same hosted packet. Each runs the original 1080p camera pass and a live worker pass. The prepared stage uses available playback time, with no readiness wait. The fresh stage starts every calculation at submission. Each report retains the individual observations and the ≤100 ms p95 result for already prepared, in-flight and fresh requests. The visible interval ends at application GPU completion. Empty groups have no timing verdict. Exact replay and meeting a latency budget are independent results.
